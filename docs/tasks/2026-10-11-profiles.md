# Profiles milestone — big-picture steps 11–14

Delivers the profile entity end-to-end: a `profiles` table, service-layer
CRUD, a seeded "Default" profile, profile management in settings (list,
create, rename), and switching from the main navigation — with the active
profile restored across restarts.

Out of scope (later roadmap steps): settings import/clone (step 47), profile
deletion (step 48), tasks/other entities keyed to profiles (they arrive with
their own features — nothing else exists yet that a profile can own).

## Deferred items

Conscious omissions made during this milestone — each notes where the work
resumes so nothing is silently dropped:

- **Settings import/clone UI** — the spec's edit-profile flow includes it;
  deferred to roadmap step 47. The Task 4 edit affordance omits it rather
  than shipping a dead control.
- **Profile deletion** — deferred to roadmap step 48 (includes the
  type-to-confirm prompt and cascade). FK `ON DELETE CASCADE` support is
  already in place.
- **`last_profile_id` validation edge case** — if the stored profile was
  deleted in a later version, startup falls back to the first profile; no
  user-facing repair flow until deletion exists (step 48).
- **Profile switching reseeds nothing** — when tasks/settings land keyed to
  profiles, verify the active-profile change actually scopes queries; that
  wiring belongs to the first profile-owned entity.
- **`active_profile_id` defaults to `0`** when no profiles exist yet (the
  `AppState::new`-before-seed window). Every production path seeds first so
  it's unreachable today; if it ever bites, the fix is `Option<i64>` plus a
  `None` case in `current_profile` — decided 2026-10-12 to defer.

## Review Focus

- **Active-profile state**: the "current profile" is a _selection_, not data —
  held in `AppState` and persisted as `last_profile_id` in `config.json`
  (the app-level layer, same as the db path). Profile rows hold only name +
  audit timestamps. Do not add an `active` column to the profiles table —
  activation is runtime state, and "last used" is a property of the machine,
  not the profile.
- **First-run profile**: `seed()` inserts the "Default" profile so the app
  always has exactly one active profile and the nav footer is real from day
  one (it already renders "Default" as a placeholder).
- **Cascade behavior**: deleting profiles is out of scope, but `tasks` etc.
  will later `REFERENCES profiles(id) ON DELETE CASCADE` — the FK pragma is
  already on, so no extra work needed here.
- **Validation boundary**: name validation (required, non-empty, trimmed)
  lives in the Rust service layer; the frontend may mirror it for UX but the
  backend is authoritative.
- **Switching is not connection state**: `switch_profile` changes only
  `AppState.active_profile_id` + `config.json`. It does not reconnect the
  database — profiles live _inside_ one db file.

## My calls (user did not decide)

- `id INTEGER PRIMARY KEY` for profiles — sqlite rowids are the simplest key;
  no uuid dependency needed.
- Timestamps as `TEXT` ISO-8601 (`datetime('now')` defaults in SQL) —
  sqlite-native, sortable, no chrono dependency for now.
- Service layer: `src-tauri/src/profiles.rs` — free functions taking
  `&SqlitePool`, returning domain structs. Commands stay thin wrappers.
- Naming collision note: the db-path command returns the db _file_ path —
  profile commands use `profile_`-prefixed names to stay unambiguous.
- New screens (profile settings section, create dialog, nav switcher) go
  through Stitch first per AGENTS.md — one screen covering the settings
  profile section + list suffices; the nav footer switcher is a small
  adaptation of the existing shell design.
- "Import settings from another profile" UI is _designed_ in Stitch during
  Task 4's screen pass only if trivial to include; no functionality ships.
